Overview

The operator's reference. It assumes you have the plugin installed and want to know what is running: which actors exist and what each one is allowed to write, the states a bolt's work moves through, and how to work on the flywheel itself. The home page teaches the shape of the thing; this page is the map you keep open beside it.

The actors

Two loop programs, four agent profiles, three persona lenses. Each actor owns a write scope, and the scopes do not overlap.

The loops are programs, not agents: flywheel server is a daemon you start on any host, and every 60 seconds it starts one stateless loop process per milestone the tracker gives a job to, and stops those without. A profile exists where a mind is needed and nowhere else.

Grey boxes are write scopes. The books and the context map are the one scope more than one actor writes, and that is deliberate: they are the destination, and every loop reads them. Nothing here messages anything else — every arrow into a loop is a tracker query, and every arrow out of a session is a commit, an item comment, or a label.

The user-* profiles — data scientist, DevOps engineer, app developer — are personas: lenses a review session reads built work through, never actors, never owners.

Three consequences worth stating outright

  • A session closes what it was charged with; the loop opens what it discovered. In its own worktree a session checks off exactly its assigned task lines and writes the decision records for questions it closed firsthand; the loop is sole writer on main, and its merge is what admits a session's work. A loop, symmetrically, never edits inside a session's directory.
  • Dispatch is the only actor bridged to a human. A question a construction session cannot answer travels out through dispatch — resolved change → owner → DM — and the answer comes back as a comment on the item that raised it, never to a different actor, and never as an edit to that bolt's change.
  • Nothing messages anything else. The tracker is the only bus: a discovery is an issue, an escalation is a label, a completion is item state, and each consumer — server, bolt loop, intent loop, dispatch — reads one exact filter over it.

Inside a bolt

Every row of the registry is in exactly one of these states.

One bolt is one construction iteration, tracking a registry of proposals across however many repositories the work touches. A bolt exists only because you approved it, which is why it can run without you: the one approval you gave covers everything inside it. 

stateDiagram-v2
  direction TB
  [*] --> to_spec
  to_spec : to-spec
  in_review : in-review

  to_spec --> specced : spec agent, validated
  specced --> in_review : independent reviewer
  in_review --> approved : verdict
  in_review --> to_spec : bounced — one round only
  approved --> building : apply agent, nested worktree
  building --> built : commit stage, then the pre-merge checks
  built --> verified : batched acceptance on the bolt branch
  verified --> merged : the full run of checks before a bolt lands
  merged --> [*]

Spec review is bounded to one round. A bounced review returns the row to to-spec — once. After that the row takes one binary call on the evidence in hand (approve, or re-spec from the decision record that settled it) and then builds, because further rounds converge on wording rather than on whether the thing can actually be built. What is bounded is reading: the commit stage, the pre-merge checks, the batched acceptance run and the full run of checks before a bolt lands never relax. Adversarial agent review plus automated testing is what earns the loop its automated delivery, and weakening either of them is a design decision, not a call the loop makes for itself.

Working on the flywheel itself

The install commands are bypassed while you are editing the plugin.

Point Claude Code at a checkout and reload in place — no publish, no reinstall, no version bump between an edit and trying it. 

claude --plugin-dir /path/to/flywheel/main
/reload-plugins

The first command starts the session against your working tree; the second, run inside that session, picks up an edit you have just made.
